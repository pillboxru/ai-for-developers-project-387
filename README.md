Продолжение проекта [«Календарь звонков»](https://github.com/pillboxru/ai-for-developers-project-386): приложение перенесено оттуда целиком, здесь агент работает внутри GitHub-процесса — в issue, pull request и по расписанию. План развития: [`docs/roadmap.md`](docs/roadmap.md).

## Стек

- Бекенд: [Fastify](https://fastify.dev/) + TypeScript
- Фронтенд: [Vite](https://vite.dev/) + React + [Mantine](https://mantine.dev/)
- Тесты: [Vitest](https://vitest.dev/), [MSW](https://mswjs.io/), e2e — [Playwright](https://playwright.dev/), линтер: [oxlint](https://oxc.rs/) + [Prettier](https://prettier.io/)
- Сборка и запуск: npm workspaces, GNU Make, Docker
- CI: GitHub Actions, релизы: [release-please](https://github.com/googleapis/release-please)

## Установка

Нужны Node.js 24, GNU Make и Docker. На Windows make ставится через [Scoop](https://scoop.sh/): `scoop install make`.

```bash
git clone https://github.com/pillboxru/ai-for-developers-project-387.git
cd ai-for-developers-project-387
make setup
```

`make setup` ставит зависимости и Chromium для e2e-тестов (отдельно Chromium ставит `make e2e-install`).

## Использование

```bash
make dev      # бекенд на http://localhost:3000, фронтенд на http://localhost:5173
make check    # линтер, тесты, сборка и e2e-тесты — то же, что гоняет CI
make e2e      # только e2e-тесты Playwright против собранного приложения
```

Контракт API описан на TypeSpec в `contract/main.tsp`. `make generate` собирает из него OpenAPI и генерирует SDK фронтенда и типы бекенда. `make dev`, `make test` и `make build` запускают генерацию сами, сгенерированные файлы в git не хранятся.

Запуск в Docker (приложение откроется на http://localhost:3000):

```bash
make docker-build
make docker-run
```

Порт задаётся переменной окружения `PORT` (по умолчанию `3000`). Имя владельца — `OWNER_NAME` (по умолчанию «Владелец календаря»), его часовой пояс — `OWNER_TIME_ZONE`, IANA-имя (по умолчанию `Europe/Moscow`); с неверным поясом сервер не стартует.

E2E-тесты поднимают сервер на порту `E2E_PORT` (по умолчанию `3100`): `make e2e E2E_PORT=3145`.

## Деплой

Приложение опубликовано на Render: https://ai-for-developers-project-387-nrdx.onrender.com/

Render собирает образ из `Dockerfile` и передаёт порт в переменной `PORT`. Бесплатный сервис засыпает без запросов, поэтому первый запрос после простоя может идти до минуты.

Данные хранятся в памяти процесса (ADR 0001): типы событий, расписание и бронирования сбрасываются при каждом перезапуске, новом деплое и засыпании сервиса.

### MCP Render для агента

Деплоем и проверкой сервиса агент управляет через [Render MCP](https://render.com/docs/mcp-server). Claude Code читает сервер из `.mcp.json` в корне репозитория. Этот файл содержит ключ и исключён из Git, в репозитории лежит шаблон `.mcp.json.example`.

1. Создайте API-ключ в Render: Account Settings → API Keys (https://dashboard.render.com/u/settings?add-api-key).
2. Скопируйте шаблон: `cp .mcp.json.example .mcp.json` и замените в `.mcp.json` `<RENDER_API_KEY>` на ключ.
3. Запустите `claude` в корне репозитория и одобрите сервер `render`. Проверка: `claude mcp list`.
4. Попросите агента выбрать рабочее пространство Render: «Set my Render workspace to <имя>».

Ключ даёт доступ ко всем сервисам аккаунта, в том числе к деплою и переменным окружения: не коммитьте `.mcp.json` и не вставляйте ключ в чат с агентом. Перед коммитом `git status` не должен показывать `.mcp.json`.

## Агент в GitHub

В issue и pull request работает агент [OpenCode](https://opencode.ai/docs/github/). Он запускается в GitHub Actions, отвечает комментариями от `opencode-agent[bot]` и берёт правила проекта из `AGENTS.md`.

### Как позвать

Команда пишется в начале комментария или после пробела. Звать агента могут только участники репозитория.

| Команда                        | Что делает                                                                    | Модель                                             |
| ------------------------------ | ----------------------------------------------------------------------------- | -------------------------------------------------- |
| `/oc` или `/opencode` и задача | Разбор (`/oc explain`), план, исправление с PR (`/oc fix`), правки в ветку PR | Sonnet 5.5, в треде с меткой `critical` — Opus 5.5 |
| `/opus` и задача               | То же                                                                         | Opus 5.5                                           |

Для глубокого разбора добавьте `@analyst` в комментарий с командой: разбор сделает субагент на Opus 5.5 без правок кода, а ответ напишет основной агент. Комментарий с одним `@analyst` без команды агента не запускает.

Звать можно в issue, в обсуждении PR и в комментарии к строке diff: там агент получает файл, строку и окружающий diff. Комментарий к строке PR из форка агента не запускает.

- Метка `critical` на issue или PR переводит на Opus все вызовы в треде.
- Sonnet сам передаёт субагенту `analyst` глубокий разбор (когда — написано в `AGENTS.md`) и пишет в ответе, звал ли его.
- По `/oc fix` в issue агент правит код и коммитит по Conventional Commits в ветке `opencode/…`, а action пушит её и открывает PR с `Closes #N`. В обсуждении PR правки уходят в ветку этого PR. Сливает PR человек.
- Вызовы в одном issue или PR идут по очереди, и ждать может только один. Если третий вызов придёт, пока второй ждёт, второй молча отменится, поэтому замечания в треде собирайте в один комментарий с командой.

### Что работает само

Когда запускается каждый воркфлоу и на какой модели, сведено в таблицу [«Воркфлоу»](#воркфлоу).

- **Автотриаж** (`.github/workflows/opencode-triage.yml`) пишет, что затронуто, чего не хватает и ответственная ли задача, а ответственной ставит метку `critical`.
- **Авторевью** (`.github/workflows/opencode-review.yml`) пропускает черновики, PR ботов и PR из форков. Замечания приходят комментарием, код ревьюер не меняет.
- **Ночная проверка Lighthouse** (`.github/workflows/opencode-lighthouse.yml`): Lighthouse проверяет опубликованное приложение, а агент разбирает выжимку отчёта и пишет итоги. Воркфлоу публикует их в issue с меткой `lighthouse`: создаёт его или дополняет открытое комментарием. Агенту доступны только файлы отчёта, без shell и токена GitHub. Полный отчёт сохраняется артефактом `lighthouse-report` прогона.

Прогоны каждого воркфлоу открываются по ссылке в первом столбце. Ответ агента в треде заканчивается ссылкой `github run` на свой прогон, а в итогах Lighthouse есть ссылка на прогон с артефактом `lighthouse-report`. У всех агентов служебная `small_model` (заголовки сессий) — Haiku 5.5. Параметры `variant` и `agent` в воркфлоу не заданы: модели работают с уровнем рассуждений по умолчанию, основной агент — встроенный `build`, а запреты на правки задают разрешения в `OPENCODE_CONFIG_CONTENT`.

### Почему настроено так

- **Нет петли.** Ответ агента — тоже комментарий, поэтому каждый воркфлоу агента пропускает события ботов, в том числе самого `opencode-agent[bot]`: `opencode.yml` и `opencode-triage.yml` по `user.type`, `opencode-review.yml` по логину автора PR и того, кто запустил событие, `opencode-lighthouse.yml` — ручной запуск от бота. Условие стоит на job: комментарий без команды даёт пропущенный прогон, который не ставит зависимости и не тратит минуты.
- **Команды заданы явно.** `mentions: /oc,/opencode,/opus`: к набору по умолчанию добавлен `/opus`, которым зовут агента на Opus. Условие `if` в `opencode.yml` проверяет тот же набор, причём команда должна стоять в начале комментария или после пробела: иначе job запускала бы и ссылка `https://opencode.ai/...`.
- **Звать агента могут только участники** (`OWNER`, `MEMBER`, `COLLABORATOR`): репозиторий публичный, и любой `/oc` от прохожего тратил бы минуты и токены. Автотриаж оценивает только issue участников, авторевью — только PR из этого репозитория. Комментарий к строке PR из форка агента не запускает: checkout взял бы код форка, и `npm ci` выполнил бы его скрипты в job с `id-token`.
- **Права выданы по воркфлоу.** Токен раннера по умолчанию только читает (Settings → Actions → Workflow permissions). Агент пишет комментарии, коммиты и PR правами GitHub App, которые получает через OIDC, поэтому воркфлоу агента нужен `id-token: write`, а остальное на чтение. Запись есть только там, где создаются задачи, коммиты или PR: job `label` в `opencode-triage.yml` ставит метку (`issues: write`), `release-please.yml` открывает PR релиза (`contents` и `pull-requests: write`). У воркфлоу Lighthouse права на запись (`contents`, `pull-requests` и `issues: write`) — требование проекта к задаче по расписанию: она создаёт задачи и PR. Сейчас PR она не открывает: агенту можно писать только `lighthouse/issue.md`, токен раннера ему не передаётся, он работает правами GitHub App через OIDC.
- **Расходы.** Модель подобрана под задачу: Haiku для оценки issue и выжимки Lighthouse, Sonnet для обычных задач и ревью, Opus только для ответственных и глубокого разбора. У каждого job свой `timeout-minutes`, разрешения, которые спрашивают человека, запрещены, чтобы прогон не висел до таймаута. Сверху расход ограничивают бюджеты в Console.
- **Сессии не публикуются.** Для публичного репозитория action по умолчанию публикует сессию агента по ссылке вместе со всем, что агент прочитал, запустил и вывел. Во всех воркфлоу агента стоит `share: false`: итог агент пишет в тред или в issue, лог прогона и так открыт, а публичная сессия стала бы ещё одним местом, куда может утечь секрет.

### Настройка

- На репозиторий установлен GitHub App [opencode-agent](https://github.com/apps/opencode-agent).
- В секрете `OPENCODE_API_KEY` лежит ключ сервисного аккаунта рабочего пространства OpenCode Console. Модели `console-anthropic/*` идут через шлюз Console на подключённый аккаунт Anthropic: токены оплачивает Anthropic, а Console учитывает расход в бюджете сервисного аккаунта. Адрес подключения задан в `OPENCODE_CONFIG_CONTENT` в воркфлоу.
- В переменной репозитория `APP_URL` (Settings → Secrets and variables → Actions → Variables) лежит адрес приложения для проверки Lighthouse.
- Расходы ограничивают бюджет сервисного аккаунта в Console и Spend limits в Claude Console.

### Самооценка

PR с воркфлоу (#1–#19, кроме #9) готовил локальный агент Claude Code в терминале, а агент в GitHub их ревьюил. Возврат прав на запись воркфлоу Lighthouse сделал агент в GitHub по #22.

С первого прохода:

- `/oc fix` по #2 открыл PR #9 сразу: агент написал тесты, которые падали из-за бага, потом правку, `make check` зелёный. Перед этим в треде была итоговая постановка с критериями.
- Замечания ревью к PR #9 (тест на страницу расписания, комментарий без истории правки, сброс `focusManager` после теста) агент закрыл по одному вызову на замечание.
- Автотриаж #6 и #16 верно назвал затронутые слои и ответственность: #6 получил метку `critical`. Разбор #6 на Opus сразу показал, что это не баг, а заложенное поведение (глоссарий, ТЗ, контракт).
- Первый же прогон Lighthouse создал #15, из его пункта 10 вышла задача #16.
- Авторевью нашло настоящие дыры в воркфлоу Lighthouse: ключ Console мог утечь в публичный заголовок через `--title`, а токен App — из `.git/config` (#13, #14). PR #19 и #20 оно приняло без обязательных замечаний.

Потребовали итераций:

- Разбор #2. Первый `/oc explain` ошибся: агент решил, что перечитывание списка не снимет пометку «Идёт сейчас», и сам исправился во втором ответе. `@analyst` нашёл в плане ещё одну ошибку и пробелы: полночь владельца, отмену при открытой модалке.
- Прогон [40205123989](https://github.com/pillboxru/ai-for-developers-project-387/actions/runs/40205123989) завис на запросе разрешения `external_directory`, его отменили вручную. После этого все разрешения, которые спрашивают человека, в Actions запрещены (#4).
- В PR #9 комментарий к строке и общий комментарий запустили два прогона параллельно, и оба пушили бы в одну ветку. Появилась очередь вызовов в треде (#11).
- Воркфлоу Lighthouse после первого PR (#13) дорабатывался по ревью ещё четыре раза (#14, #17, #18, #19), пока не закрылись все найденные пути утечки секретов в публичное issue.

Итог: задачу с чёткой постановкой и критериями агент закрывает с первого прохода. Без постановки его разбор стоит перепроверять вторым вызовом или через `@analyst`. Больше всего итераций ушло на окружение агента: права, очередь, защиту публичных ответов.
